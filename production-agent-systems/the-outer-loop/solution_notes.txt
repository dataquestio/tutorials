WHAT TO DO

The root is Course 2's own starter: every Section 7.1 file (agent.py, tools.py, tracing.py,
memory.py, skills.py, permissions.py, run.py, skills/) written for this course, plus the feed
tools in tools.py (day_summary, apply_day_to_catalog, flag_anomaly, append_progress, send_alert).
A learner who finished Course 1 should recognize every name. Spend the first screens on a short
tour of it (Section 10.2), then run run.py once on a single day.

The lesson adds runner.py:

- run_day(day, state_dir, config, client=None): fresh run_agent conversation per day, then
  commits state.json (current_day, completed_days, tokens_used_total, pending_approvals).
- Exit criteria in run_range: end day reached, total token budget, or an "error" stop.
- Budgets: AgentConfig.max_tokens_total is per run (--max-tokens-per-day); --max-total-tokens
  is across runs.
- Unattended approvals: permissions.APPROVER is swapped for queue_for_human, so "ask" tools
  (send_alert) land in pending_approvals instead of blocking on input().
- Crash safety comes from two habits: state.json and catalog.jsonl are written to a temp file
  and swapped in with os.replace, and apply_day_to_catalog is idempotent (a row whose
  `updated` matches the stored version is skipped). A killed day is simply run again.

Teaching points the measured run produced (worth a screen each):

- The kill landed after day 5's agent finished but before state.json was committed (one
  measured run left a half-written "[runner] 2026-06-05: stop=final" line in progress.md). The
  restart repeated day 5. Because apply_day_to_catalog is idempotent, the repeated run reported
  "0 new, 0 revised" for that day: correct for the catalog, misleading in progress.md. That is
  the cost of committing once per day, and the motivation for lesson 2.
- flags.jsonl and progress.md are append-only, so a repeated day can write its flags twice.
