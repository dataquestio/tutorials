WHAT TO DO

Build the lesson in three beats. The measurements below are what each beat shows.

1. The dry run. Run the loop with the offline heuristic judge. It returns
   `not_applicable` for relevance, so decide_next_action cannot decide and no retry
   ever fires. Free, deterministic, and the whole point of the flag.

2. The proof. Two things to establish:
   - The heuristic's faithfulness score cannot fail. parse_citations only returns
     ids already in the retrieved set, so "cited ids are a subset of the supplied
     evidence" is close to a tautology.
   - The failures that matter are not fabrications. cherry_pick answers `git rebase`
     with git-rebase(1) as its top retrieved chunk; worktree answers "switch between
     branches". Both are real, documented, retrieved commands. Both address the
     question. They are just the wrong tool, and seeing that takes Git knowledge.

   So a substring rule cannot make this call, and neither can an evidence-only
   judge: an answer supported by its evidence always passes.

3. The live run. Wire in llm_judge with the relevance dimension. Retries fire only
   where they should, and both get fixed.

Then a fourth screen: the metric versus the system. Four cases answer correctly
while their answer key is never retrieved. self_rag.py prints relevance beside
answer_key_missing for exactly this. AR1 already teaches this shape with the
`git branch -d` false positive, so this extends a thread rather than starting one.

Lead that screen with revert_merge: the pipeline answers `git revert -m 1` correctly
in 3 of 3 runs from the revert-a-faulty-merge howto, while the designated key sits
at rank 13 and never arrives.

Use cherry_pick to teach that an LLM judge is not a stable arbiter on an ambiguous
question, and as the reason max_retries exists. Do not present it as a second clean
success.


ASSUMPTIONS

- relevance may use general Git knowledge. That exception is scoped to this one
  dimension because it drives a decision, not a grade. The other four stay
  evidence-only.
- relevance is scored by a second request, so llm_judge costs two calls per
  judgement. Folding it into JUDGE_SYSTEM_PROMPT does not work: the "SUPPLIED
  EVIDENCE ONLY" instruction governs the whole request and overrides a contradicting
  one inside it. Worth teaching in its own right.
- heuristic_judge returning `not_applicable` for relevance is the design, not a gap.
  Do not make it partly capable; beat 2 depends on it.
- The retry trigger is relevance < 4. The failing cases score exactly 3.
- The retry query is built from the judge's better_tool field, so it works on any
  query rather than only on cases carrying a known tag.
- Judge calibration relevance scores live in judge_calibration_relevance.jsonl, a
  separate overlay keyed by example_id. EO2's judge_calibration_examples.jsonl must
  stay byte-identical, because EO2's lesson prints an expected_scores row from it.
  The 15 relevance scores are author judgements and need review.
- expand_query runs at temperature 0.3, so borderline cases can flip between runs.
  Both demo cases held across 3 runs each. If you promote a borderline case to a
  demo, pin the reformulations first via expand_and_retrieve's `reformulations` arg.
- AR2 makes live judge calls, so AR1's free-dry-run promise does not carry forward.
  The setup screen needs its own cost paragraph.

Do not build a danger narrative around revert_merge. All three runs lead with the
correct `revert -m`. One mentions `reset --hard` as a secondary option and carries an
explicit data-loss warning, which is AR1's warning rule working as designed.
