WHAT TO DO

Guided project. The learner builds ProductionHarness themselves, in OOP, with little
hand-holding, so production_gitquest.py is the reference solution rather than taught
code.

Treat the handler contract comment in that file as the project spec. Whatever it
says is what a learner's own handler has to satisfy:

  (case, config) -> (result, judgement)

The three things worth briefing explicitly, because they are what makes the harness
a harness rather than a script:

- the case-handler registry, so a new failure mode is a one-liner from outside the
  harness rather than an edit to the orchestrator
- cost_per_passing_answer_usd, which answers what a budget owner actually asks
- run_canary, per-item paired runs across two configs, so behavioural drift surfaces
  before a config change is promoted

Point learners at self_rag_retry_handler as the pattern to copy. It is the shorter of
the two handlers and it gets the judge's evidence argument right.


ASSUMPTIONS

- This asks for the learner's first class in the whole GitQuest sequence. Nothing in
  Intro to RAG, EO1-EO3, or AR1-AR3 exercises class, __init__, self, @staticmethod,
  or a registry pattern. Whether that is fine depends on what the platform requires
  upstream of the AI engineering path. If OOP is taught earlier, state it in the brief
  as a prerequisite. If not, this is a large unaided ask.

- The metric split matters more than anything else here, and it is easy to get
  backwards:

    retrieval_recall_at_k, retrieval_mrr     the answer key (gold_evidence)
    citation_precision, citation_recall      the answer key (required_citations)
    faithfulness, citation_correctness       the chunks the model was GIVEN
    relevance (AR2 onward)                   the question, using Git knowledge

  Both judges define faithfulness as "are the cited ids a subset of the supplied
  evidence". Hand a judge the answer key instead and it answers a different question,
  "did the pipeline cite what we expected", which is citation precision under the
  wrong name. Symptom to recognise: real citations reported as invented, and
  faithfulness that never reaches 5.

  evidence_payload() exists for hydrating curated chunk ids when you want to inspect
  an answer key. It must not be passed to a judge as evidence, and its docstring
  says so.

- EVAL_ITEM_CASE_TYPE is "default" because curated eval items only ever carry
  answer / clarify / refuse. `retrieve_again` reaches the code only via overlay cases,
  which dispatch on case_type instead. The constant keeps the override hook.

- The judgement dict carries relevance as the string "not_applicable" under the
  heuristic judge. That never reaches arithmetic: monitoring aggregates only
  metrics["faithfulness_score"], a float or None.


EXPECTED RESULT

Verified: production_gitquest.py runs end to end. At --limit 2 that is 4 run
logs, pipeline_version gitquest_ar2_v1.

Decide before authoring the threshold-clearing screen: avg_faithfulness_score
does not reliably clear AR3's 4.0 threshold at small --limit values. Generation
temperature is not pinned (same fact as EO3's Beat 2 point 3), so at n=4
individual item scores of 3 and 5 can average out right at 4.0 instead of
comfortably above it. Either demo with a larger --limit so the average has
less variance, or use the noise itself as the teaching point, the way EO3 and
AR3 already do elsewhere.

Both handlers default to heuristic_judge, not a live judge call (run_self_rag_loop
falls back to heuristic_judge when no judge is passed, and secured_pipeline_handler
calls it directly). A live judge can be wired in via run_self_rag_loop's judge
argument; decide whether this lesson demos that or stays on the heuristic default.

Cost: --limit 8 means 8 eval items plus 8 advanced cases, each a full pipeline run
with generation. Budget before demonstrating a full batch.

Budget for a full --limit 38 run (all 38 advanced cases, all 7 case types, plus
38 curated eval items): roughly 82 generation calls (curated items and all
advanced cases except self_rag_retry are single-pass; the 6 self_rag_retry
cases can take up to 2 passes each at DEFAULT_MAX_RETRIES=1). Cost lands
around $0.03-0.05, wall clock around 12-15 minutes, sequential with no
parallelism in the harness. Use this for the lesson's own cost/time framing
rather than re-deriving it per author.

FORWARD OPTION, NOT A DEFAULT

With AR2's relevance-driven loop in place, AR4 could route every curated eval item
through the self-RAG handler, since the loop no longer needs an answer key to decide
whether to retry. That doubles the pipeline passes on a batch run, so it is a
deliberate choice for whoever writes this lesson.


STRETCH EXERCISES: RE-RUN EO3/AR3 FUNCTIONS ON THE REAL AR4 DATA

EO3 and AR3's own screens run their monitoring functions against synthetic or
single-case-type data (make_degraded_copy, drift_snapshots.jsonl, the
single-bucket regressions_by_slice call). production_gitquest_run_logs.jsonl
is the first real, case_type-diverse live dataset in the repo, so these
functions can be re-run against it for genuine results instead of fixtures.
main()'s CLI only exposes --rag-dir, --limit, --output-log, and --canary; a
second differently-configured run needs the ProductionHarness Python API
directly (a second config dict passed to a new harness instance), not a CLI
flag.

- regressions_by_slice, for real per-slice results. Run production_gitquest.py
  twice with two different configs (e.g. token_budget or model changed), and
  pass both run sets to regressions_by_slice. AR3's own notes ship this
  single-bucket for lack of case_type data; this file has all 7 case types.

- compare_models, at full AR4 scale. EO3's compare_models comparison
  (gpt-4o-mini vs gpt-5-nano) only covers the 24-item curated set. Running the
  same two-model comparison through production_gitquest.py's full 76-item
  batch (curated items plus all 7 advanced case types) tests whether the
  cost-vs-latency story holds up across security and self-RAG cases too, not
  just plain Q&A.

- time_series_drift, with genuine snapshots instead of synthetic ones. Run
  production_gitquest.py 3-5 times (same config, different labels) and feed
  the results in as real timestamped snapshots. Generation temperature is not
  pinned, so the natural run-to-run variance becomes real drift data rather
  than the deterministic degradation used in EO3's drift_snapshots.jsonl.

- run_canary itself has not been exercised in this session's verification runs
  (neither run used --canary). Running with --canary is the cheapest of these
  four to try, since it reuses the existing batch rather than requiring a
  second full run, and it is the one AR4 feature none of the above stretch
  exercises touch.
