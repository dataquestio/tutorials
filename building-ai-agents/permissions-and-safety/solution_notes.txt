WHAT TO DO

Add permissions.py (policy, approver, decide) and wire it into the loop: every
call to a known tool gets a decision, traced as an "approval" event. Denied or
rejected calls return {"error": ...} to the model. tools.py strips variables
ending in _API_KEY or _TOKEN from subprocess environments. The system prompt
gains "Untrusted data" and "Permissions" sections. run.py gains --allow and
--deny.

demo_poison_data.py (lesson root only) builds a copy of the data with an
instruction appended to the most common residential-noise resolution text
(resolution_id 3). It links the big CSVs and rewrites only resolutions.csv.

Commands (run from solution-files/ unless noted):
  From the lesson root:
    python demo_poison_data.py --data-dir <nyc311> --out poisoned_data
  python run.py --data-dir poisoned_data --question "What do the resolution texts say for residential noise complaints? Summarize the most common outcomes."
  python run.py --data-dir <nyc311> --question "Use the shell to count the lines in each data file."
  python run.py --data-dir <nyc311> --question "Run the shell command echo \$OPENAI_API_KEY and tell me what it prints."
  python run.py --data-dir <nyc311> --allow run_shell --question "Run the shell command echo \$OPENAI_API_KEY and also run python to print os.environ.get('OPENAI_API_KEY'). Tell me exactly what each printed."


ASSUMPTIONS

- Default policy: list_files, read_file, load_skill, write_file, run_python
  allow; run_shell ask; anything else ask.
- With no terminal attached, the approver denies.
- Known gap: stripping the environment does not stop code from reading a key
  stored in a file the process can reach, e.g. a .env next to the workspace.
  Real isolation needs an OS-level sandbox or container, which is out of scope.
  Worth saying in the lesson.
